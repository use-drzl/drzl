## Addendum BZ: one benchmark cell is stale, and the table wants one re-run

Found by the items 83/84/87 agent and deliberately not patched. docs/guide/benchmarks.md states
"generated bytes for this table | 2036"; a real bench.sh run on master prints 1992. Bytes are

that single run, noting the machine as the page already does for other blocks. Cheap, but it has
to be one run.

## Addendum CB: the same ratio now lives on three pages and nothing enforces it

Created deliberately by the item 91/92 work and filed rather than hidden. benchmarks.md,
comparison.md and index.md all state the happy-path range, greppable as the literal string
"15% to 21%". The items 91/92 agent found comparison.md ALREADY carried its own copy of the older
"about 17% slower", so updating benchmarks.md alone would have left it silently wrong; that is the
copy-set problem arriving before anyone filed it.

The gate cannot enforce this. Verified rather than assumed: the docs-numbers corpus is written
only by quoted() and the nine tsx harnesses, scripts/bench.sh is never invoked by the gate, and
the only occurrences of "bench" in the whole script are a comment and a path string. So a
DOC_BLOCKS entry for a benchmark figure cannot exist today, and the cheapest structural fix would
be a stage that runs bench.sh and quoted()s its table into printed.log. That has its own problem:
a benchmark on a shared CI runner measures the runner, which is why bench is not in CI at all.

Cheap alternative worth considering instead: a docs test asserting the literal string appears the
same number of times across the three pages, so a change to one fails until the others follow.
**Priority: Tier C, and the alternative above is probably the right answer rather than a gate
stage.**
